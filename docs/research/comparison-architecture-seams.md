# Architecture seams for the comparison program (issue #397)

Assessment against `origin/main` at `820373c` (2026-10-17). “Exists” means a public contract plus delivered implementation/registration; it does not mean every combination is supported. “Declared” means modeled or planned but without a complete production adapter. Facts below distinguish framework seams, provider instances, and measured end-to-end substitution.

## Owner-accepted items

1. **Approximation registrations with inner/outer policy:** partially delivered beyond the earlier draft. The port, registration selection path and independent structural evidence filter are now executable. There is not a general production suite of nontrivial approximation producers; no generic error-bound verifier exists. Heuristic output stays heuristic; provider-declared inclusion alone does not pass.
2. **Production strategy registration and family boundary (SYN-07/#155):** registrations, typed StrategyPort, capability admission and compiled profile verifier exist. Actual A/B strategy implementations exist. However, broad complete/partial family correctness remains fail-closed; #155 is still open. `framework-composition.md` says Strategy A/B general nominal paths yield numerical candidates, while exact completeness applies only to reviewed profiles.
3. **Automated substitution sweeps / paired comparison records (EXP-02/#94):** `src/application/comparison.cpp` has a real guarded paired application flow, but it is not a configurable sweep: constants restrict it to two T-S profiles, reach-back plus direct-joint strategies and H-family representation (`:11-27`). It prepares both strategies against one resolved problem, then runs them and verifies selected witnesses (`:38-85`). `encode_strategy_run` persists one strategy projection; comments/type say paired comparison and verifier reports remain in memory (`include/csl/application/comparison.hpp`, `src/application/comparison.cpp:145-190`). The saved `reports/algorithm-results/syn-ts01-paired-20261014-b7f1ac0/README.md:1-11` is a measured seven-pair T-S01 report with inconclusive timing and omitted live proof payload, not a general substitution sweep or scalable report codec. #94 remains open and explicitly asks for broader axes and saved repeated records.
4. **Conversions beyond Qhull:** missing for the requested unbounded/ray fairness. The Qhull adapter is bounded and rejects those forms; no alternative backend implementing ray-capable conversion was found. Same-representation passthrough does not create cross-representation fairness.

## Task-generality scan

- **Generic by contract:** `LinearSystem` dynamics, observation, dimensions and coefficient providers do not name fuel; `ResolvedProblem` composes an arbitrary model, controls, initial/external data, constraints and objective. `StrategyPort` operates on that resolved problem, rather than a four-state fuel object. These are real seams for new models/tasks.
- **Fuel-specific support is intentionally in adapters/consumers:** the dossier contains 4-state fuel matrices and physical simulation; plotting issues include selectable fuel coordinates (#91/#98). Such domain-specific replay/plot adapters should not be mistaken for model-core coupling.
- **The current paired app is fixture-specific, not fuel-hardcoded:** `src/application/comparison.cpp:11-27` hardcodes the synthetic T-S01/T-S02 profiles, two strategy IDs, and H representation. This is a genuine task-scope restriction but it is not fuel coupling; the code cannot be generalized by merely adding an unrelated fuel model without broadening its admission and report contracts.
- **Strategy algorithms still impose profile/capability assumptions:** general A/B nominal paths have limited outcome scope, with built-in complete-family routes for exact scalar integrator profiles. The API is generic, but not every model/objective/domain is accepted (`framework-composition.md`, “Supported synthesis profiles”; strategy capability functions in `src/synthesis/`).
- **Reports are mostly saved-result/rendered artifacts, not task adapters:** the rendering pipeline can be backend-neutral, but the current measured paired result is T-S01-only. `framework-composition.md` says report tooling reads saved records without solver calls and explicitly identifies missing paired proof-bearing persistence. No evidence establishes a generic arbitrary-task automated comparison UI.

## Linearization seam and required future adapter

The current model contract can **represent the output** of a linearization as affine LTV stages `A_t,B_t,a_t` (and possibly disturbance/remainder channel), but it does not accept a nonlinear `f`/ODE, reference trajectory, or construct those coefficients. The implemented model snapshot accepts supplied discrete affine matrices and observation records; continuous time is unsupported (`docs/contracts/linear-model.md:1-21`). EXT-05/#54 concerns continuous-time discretization, hold/integration semantics and integration error; its issue body explicitly keeps descriptor and nonlinear models separate. It is not a nonlinear linearization adapter.

Therefore a local linearization adapter can be added without changing the **affine solver-side data shape** if it emits a conforming affine model, but a useful/valid adapter seam still needs new input/provenance and error contracts: nonlinear dynamics and differentiability domain; nominal/reference state/control trajectory and coordinate/offset convention; Jacobians and affine residual; control/state transformation; region of validity; a bound/tube on nonlinear remainder, integration and parameter error; propagation of that bound into constraints/objective; numerical/validated evidence and rejection outside assumptions. `docs/research/scientific-foundations.md:52-59` gives the Taylor model and says a justified residual bound is required for nonlinear claims; `reachability-proof-audit.md:127,143,147` supplies an example where local linear and nonlinear reachable sets contain neither one another. A plain `A,B` adapter would therefore support local prediction, not claim nonlinear reachable-set containment or control feasibility.

## Concrete gaps and weaker-than-“seamless” claims

- Registration is not interchangeability by itself: provider capability is checked for declared output/assurance, but support is often representation-, profile-, and operation-specific. The strategy admits only a narrow combination; no complete Cartesian substitution matrix or generated sweep is delivered.
- There are multiple LP providers and hull reducers, but only one general ConvexPort provider and one bounded H/V conversion backend. Do not generalize from the existence of separate port types to multiple working alternatives for every axis.
- Approximation policy admits only elementary structural enclosures; no production approximation producers with robust inner/outer guarantees or general error bounds are identified.
- The comparison API is both family/profile and strategy-count specialized. It has no general `ComparisonSpec` sweep over all axes, nor paired-run persisted artifact with proof/evidence round-trip. The report's “seven alternating pairs” is a bounded experiment, not automated architecture-wide substitution.
- `docs/architecture/modular-algorithms-and-solution-sets.md:3` still calls the “complete two-approach synthesis and optimal-family workflow” pending, while current `framework-composition.md` documents shipped narrow A/B paired composition. This overview is stale unless interpreted as general/full-profile scope; the implementation is real but guarded. ADR 0002 is accurately marked pending integration review (`docs/architecture/decisions/0002-native-integrations.md:3,65-67`); its status does not mean the selected LP/QP integrations are absent, but broader packaging, cross-platform/race and Qhull review remain.
- “Seamless” model extension understates scientific obligations: an adapter must carry coordinates, units, constraints and error evidence, not just instantiate an affine interface. Changing algorithms also changes assumptions/output family and must be admitted/reported, not forced through a common enum or silently coerced.
