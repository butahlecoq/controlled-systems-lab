# Pages learning-book audit

Audit date: 2026-11-11. Source baseline: `ed2dda1ef049ac4fbe259a800d3314e446ceee28`.
This is a source audit and implementation proposal, not a claim about the deployed site's current appearance. No solver, benchmark, native build, or browser session was run for this audit. Repository links resolve against the audited revision when read there; freeze them to this commit in any external ticket that needs permanent evidence.

## Finding

The site already contains substantial teaching material, but it has several independently owned page shells and organizes its main entry point around reports. A reader can inspect results without learning how to move from a model to an installed program, a complete-family result, or a different information pattern. The appropriate change is a book-shaped educational layer with one visual system, supported by the existing saved-data companions and report archive. It must not restyle frozen evidence in place. This follows the repository's explicit requirement to keep educational pages separate from immutable bundles and retain the existing Omarchy report appearance. [Delivery guidance](../agents/delivery.md), [publication policy](../architecture/published-algorithm-results.md), [current composition](../architecture/framework-composition.md).

## Learning transitions that are missing

The archive explains what was measured and the gallery explains visible inputs/answers; neither supplies a sequential curriculum. The gallery navigation is built from individual examples, analytic illustrations, coverage and saved figures. Its own text says the inventory does not imply every implemented algorithm has a supported 2D example. Its coverage machinery and `visual-route-inventory.json` should feed the book's map rather than be discarded. [Gallery `build`, `algorithm_coverage` and `coverage_html`](../../scripts/reports/visual_examples.py), [visual route audit](../../scripts/reports/audit_visual_routes.py), [route inventory](../../scripts/reports/visual-route-inventory.json).

Concrete teaching bridges to add:

- Build/install → external `find_package(CSL CONFIG)` consumer → first numeric answer. The README supplies working command structure and expected outputs, and `examples/CMakeLists.txt` exercises public installed targets, but the Pages gallery is not a replacement for that sequence. [README quick start](../../README.md#quick-start), [example CMake project](../../examples/CMakeLists.txt), [native build](../build/native.md).
- Authored equations/sets → immutable resolved problem → JSON identity → registry admission. A parsed or representable scenario is not automatically solvable. Contrast the caller-supplied history in `scenario_file` with the actual strategy execution in `scenario_cli`. [Resolved example](../../examples/resolved_scenario.cpp), [file example](../../examples/scenario_file.cpp), [scenario contract](../contracts/scenario-input.md), [run guide](../how-to/run-scenario.md).
- One numerical witness → joint-history optimal face → profile-specific completeness verifier → serialized recorded claim. Marginal 2D projections and decoded claims do not confer completeness. [Composition profiles](../architecture/framework-composition.md), [trajectory verification](../contracts/trajectory-verification.md), [run records](../contracts/run-statistics.md), [certificates](../contracts/certificates.md).
- Nominal continuous-action planning → fixed-plan uncertainty → causal feedback → partial observation → receding horizon. These are distinct information patterns and APIs; a report-family list hides that conceptual progression. [Information patterns](../contracts/information-patterns.md), [fixed-plan minimax](../contracts/fixed-plan-minimax.md), [finite feedback](../contracts/finite-feedback.md), [continuous policies](../../include/csl/controllers/continuous_policy.hpp), [MPC roadmap](mpc-comparison-primary-sources.md).
- Exact sets → approximate sets → effect on feasible sets and objective bounds. Teach inclusion direction and representation limits before comparisons or timings. [Approximation contract](../contracts/approximation.md), [generator sets](../contracts/generator-sets.md), [ellipsoids](../contracts/ellipsoidal-approximation.md).
- An analytic/replayed illustration → measured report → historical/source-derived reference. The reader needs evidence labels before seeing a number, especially B04/B06 and source adaptations. [Visual QA](../testing/projection-visual-qa.md), [source-variant standard](../architecture/decisions/0004-source-variant-evidence-standard.md), [owner reference decisions](owner-reference-decisions-2026-11-10.md).

## Proposed chapter map

This is a proposed information architecture, not a claim that all chapters already have a runnable tutorial. Keep the full topic map visible; label gaps explicitly. A topic can be covered by a conceptual explanation and a supported fixture without promising a general solver. The current composition document owns the module map; the comparison program owns planned comparisons and authorizes no benchmark runs. [Framework composition](../architecture/framework-composition.md), [comparison program](../architecture/comparison-program.md).

Keep the introductory prerequisites first, then organize the book around the four module groups requested by the owner. The chapter sequence inside a group is pedagogical; it does not assert that every substitution is supported by every controller. A recurring environment task provides continuity: establish fixed dynamics, horizon, constraints, objective, uncertainty/observation semantics and expected checks, then change one admitted module at a time. If a module requires different semantics or cannot solve the task, expose that mismatch explicitly instead of silently changing the task.

### Group 1. LP/simplex algorithms for vertex extraction

This group teaches the LP-based hull problem before the controller's terminal objective. Here a membership feasibility query asks whether a point is a convex combination of other points. It is a mechanism for redundancy/vertex extraction, not the control problem's terminal minimization. A conservative modern reducer may retain non-extreme points when no exact deletion certificate is available; “complete” reduction does not itself prove that the retained list is exactly the extreme vertices. [Hull-reduction contract](../contracts/hull-reduction.md).

### Group 2. Five reachable-set representations

Present the five requested teaching tracks as **polytopes, boxes, parallelotopes, zonotopes and ellipsoids**. Polytopes have H/V encodings; H↔V conversion is a supporting operation in Group 4, not a sixth representation chapter. Explain constrained zonotopes and dependency-preserving generator forms as explicitly scoped extensions where implemented, and lazy geometry as an evaluation/materialization strategy. Do not imply that all five are interchangeable behind every current Strategy A call. ## Navigation and visual acceptance proposal

Adopt a shared mutable educational shell and tokens after comparing the root, gallery and representative companions together. It should include a book entrance, chapter list with current chapter, local section list, breadcrumbs, previous/next links, a source link and an evidence link. On narrow screens the chapter list must remain reachable without consuming the whole first viewport. The current gallery already provides useful skip links, focus outlines, print treatment and reduced-motion handling; preserve those behaviors when consolidating. [Gallery stylesheet](../../scripts/reports/visual_examples.css), [gallery markup](../../scripts/reports/visual_examples.py).

Acceptance should be observable in a real browser, not merely asserted from CSS:

- Compare the book home, one geometry lesson, a runnable synthesis lesson, copied adaptive/fuel companions, a long equation/table page and report archive at 1440×900, 768×1024 and 390×844. Record screenshots and verify typography, spacing, colors, navigation and evidence labels match the approved shell. Include a short landscape viewport and 200% zoom.
- Keyboard traversal reaches the skip link, chapter navigation, local navigation, examples and downloads in a meaningful order; focus is visible; active chapter is announced; long navigation scrolls independently without trapping focus or hiding the final chapter. Verify anchor landings leave headings visible.
- No page-wide horizontal overflow at mobile width or zoom. Wide code and tables scroll in labelled regions. Math wraps or scrolls locally. Figures preserve axis labels, legends, units, coordinate order, target markers and zero/negative values; inspect full-size SVG as well as the embedded preview. [Existing fuel QA](../testing/projection-visual-qa.md).
- Screen-reader names, image alternatives and adjacent data/description communicate what the visual establishes. Check contrast for text, links, focus, graph marks and muted provenance; do not rely solely on color for algorithms, witness roles or evidence level.
- Print a representative lesson and a dense control/tube page; labels, URLs and provenance remain readable without dark panel fill or clipped plots. Test reduced-motion preference and offline loading without third-party font/script requirements.
- Follow a novice path from home to installation, scenario validation, a supported strategy run and interpretation; follow an expert path to an existing report and its raw JSON/ZIP. Check relative links, fragments and downloads in a staged site under the repository Pages base path, then verify deployed URLs before claiming publication. [Delivery verification rules](../agents/delivery.md).

These are proposed acceptance gates. This research has not passed a browser or accessibility audit.

## Preservation and delivery constraints

The immutable boundary is substantive: `site.py` validates manifest hashes and offline bundle inventory; `visual_examples.build()` explicitly validates saved records and states that it must never rewrite full report artifacts. Offline HTML validation is also restrictive: older report bundles do not permit arbitrary external stylesheet resources. Therefore appending shared CSS links or navigation to every historical `index.html` would violate evidence and offline contracts, even if it visually succeeds. [Site validator](../../scripts/reports/site.py), [gallery staging](../../scripts/reports/visual_examples.py), [published-results policy](../architecture/published-algorithm-results.md).

Before implementation, take a byte/hash inventory of all tracked report bundles, archives, manifests and staged immutable routes. After producing the book, require exact equality of that inventory and existing URLs. New educational companions may read frozen records and figures, but must retain original commit, raw source links, scientific limits and source-variant attribution. Preserve old educational deep links/anchors or supply explicit redirects/aliases; do not repurpose a versioned report route as a chapter. New publication staging must retain main-only deployment, stale-head checks, augmentation aggregation and registered catalogue validation. [Pages workflow](../../.github/workflows/algorithm-reports.yml), [augmentation aggregation](../../.github/workflows/pages-augmentation-aggregation.yml), [source variants](../architecture/decisions/0004-source-variant-evidence-standard.md), [delivery](../agents/delivery.md).

The work should be delivered as documentation/publication changes, with explicit package/release impact: ordinarily no C++ release is needed if APIs, dependencies and installed examples remain unchanged. If teaching exposes a real executable/API gap, track that separately with its own installed-consumer validation. Documentation publication alone does not require the native platform matrix. Run new numerical experiments under the existing owner authorization and published-results evidence gates; this research pass runs none. [Delivery guidance](../agents/delivery.md), [comparison-program contract](../architecture/comparison-program.md).

## Suggested implementation units

1. Inventory mutable routes, owner generators and chapter prerequisites in one machine-readable book manifest, with explicit ownership by the four requested module groups and fixed-task/module-swap relationships. Reuse gallery coverage and route audit data, and mark unsupported/no-2D topics instead of dropping them. Verify source links and ownership before shell changes.
2. Review a small representative visual set, then establish a shared educational template, token source and navigation. Migrate root/gallery and mutable companion producers together; preserve immutable views as archival destinations.
3. Publish the installation → scenario → optimization → nominal-family learning path with real commands, expected answers and one independent check per lesson. Resolve contradictions against code: for example the README still describes v7 artifacts in one paragraph while the run guide and current composition describe v10. [README](../../README.md), [run guide](../how-to/run-scenario.md), [composition](../architecture/framework-composition.md).
4. Deliver the four module groups explicitly: vertex-LP algorithms with faithful-versus-adapted comparisons; all five reachable-set representation tracks; reachable-set-based and MPC controller lessons; supporting V↔H/set/optimization operations. Use the fixed environment task as the spine, changing one admitted module at a time. Give historical comparisons and MPC/environment studies explicit evidence status and prerequisites.
5. Run link/base-path, immutable-byte, staged-site and browser acceptance checks; publish through the existing workflow and record actual deployed verification.

These are proposed task boundaries, not claimed or newly created GitHub tickets. Before any implementation claim, follow live issue discovery, native dependency verification, assignment and coordination rules; existing gallery follow-ups and comparison work may already own parts of the scope.
