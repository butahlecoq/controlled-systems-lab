# Windows profiling options for the Strategy B T-S01 report

**Date:** 2026-10-14
**Scope:** Read-only audit of the existing Strategy B profile evidence and profiler availability on the Windows measurement host. No benchmark or profiler capture was run for this note.

## Finding

The published profile did not identify a source-level limiter. WPR failed before producing a trace, and the short separate workload plus process snapshots cannot replace a CPU profile. The recorded WPR system-wide capture was unavailable to the current process token. xperf is installed, but this audit did not verify a process-scoped xperf capture path for this token. Visual Studio 2022 Community and its Performance Profiler components are installed, but whether its process-scoped CPU Usage collection works with this token has not been verified. The evidence does not justify claiming that every alternative is blocked.

## Local evidence

The versioned [profile sidecar](../../reports/algorithm-results/syn04-strategy-b-ts01-20261014-2a5ab835/profile.json) records `wpr -start CPU -filemode` failing with `0xc5585011`, `etl_path: null`, and no trace; therefore it contains no CPU stack samples. Its separate workload exited successfully, but took only **18.8142 ms** wall time. All seven process-counter snapshots report **0.0 s** user CPU and **0.0 s** system CPU; sampled peak RSS was 6,836,224 bytes. These observations do not identify a hot function or phase.

In this audit shell, `whoami /priv` listed neither `SeSystemProfilePrivilege` nor `SeProfileSingleProcessPrivilege`. Microsoft documents these as distinct rights: the former permits system profiling, while single-process profiling has its own right ([privilege constants](https://learn.microsoft.com/en-us/windows/win32/secauthz/privilege-constants), [user-right policy](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-userrights)). Microsoft’s WPR guide associates `0xc5585011` with failure to enable system profiling and directs capture from an elevated prompt ([WPR capture guidance](https://learn.microsoft.com/en-us/windows/apps/develop/performance/disk-memory)). Microsoft’s xperf CPU-sampling-by-process trace uses the ETW `PROFILE` event ([xperf CPU sampling](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/cpu-sampling-by-process)); the installed xperf binary alone does not prove that such a capture can run with this token.

Visual Studio 2022 Community is present, including Performance Profiler components. Microsoft documents that its CPU Usage tool supports native C++ and can show function/call-tree CPU data, and that it can attach to a running process ([Visual Studio CPU profiling](https://learn.microsoft.com/en-us/visualstudio/profiling/cpu-usage?view=visualstudio)). The installed tree contains report/analysis components; no standalone `vsinstr.exe` or `vsperfcmd.exe` collector was found in the inspected paths. Visual Studio’s profiler uses ETW, but its documentation does not establish whether its process-scoped capture will work with the current token ([profiler troubleshooting](https://learn.microsoft.com/en-us/visualstudio/profiling/troubleshoot-profiler-errors?view=visualstudio)). Treat that route as **available to test, not proven available**.

The duration is an independent problem: Microsoft warns that Visual Studio CPU profiling may return no data when the target completes in less than one second. The **18.8142 ms separate workload launched for the WPR profile attempt** is much shorter ([profiler troubleshooting](https://learn.microsoft.com/en-us/visualstudio/profiling/troubleshoot-profiler-errors?view=visualstudio)). Visual Studio CPU Usage was not tried; this duration is a reason to make a future diagnostic workload longer, not evidence about Visual Studio capture. Even a successful short capture would not support a stable ranking of fine-grained hot functions.

The report’s measured interval itself covers problem resolution/construction, provider and strategy registration/selection/preparation, workspace creation, public StrategyPort execution, compiled T-S01 verifier acceptance, and canonical relation/membership checks. It does not contain internal phase timings. The [measurement record](../../reports/algorithm-results/syn04-strategy-b-ts01-20261014-2a5ab835/measurement.json) explicitly marks preparation, registration, workspace creation, HiGHS QP subphases, extraction, verification, and export counters unavailable. The current evidence can support an end-to-end latency result, but no source-level or subphase limiter attribution.

## Defensible next steps

1. On this host, first verify whether Visual Studio’s CPU Usage collection can attach to the Release CMake executable with the available account rights. A failed or empty capture is evidence of a permission/tooling gap, not a limiter.
2. If capture is denied, use a permitted host or have an administrator provide the required system- or single-process profiling right. Recheck the active token and retain the successful trace/session plus exact capture command and tool version.
3. Make the separate profiling workload long enough to yield useful samples. Repeat the exact solve-and-validation operation inside the excluded profile run, consume and validate each result, and keep it out of the latency statistics. Preserve the same measured source identity, compiler/PDBs, provider configuration, load observations, and resource limits.
4. Resolve symbols for the measured executable and relevant native dependencies, and report sample counts, collection duration, dropped-event status, and the limits of the attribution. If only explicit phase timers are available, label their result as instrumented phase timing and disclose instrumentation overhead; do not describe it as sampled source-level profiling.

Until a permitted, sufficiently long profile produces interpretable evidence, the scientifically supported limiter conclusion remains **inconclusive**.
