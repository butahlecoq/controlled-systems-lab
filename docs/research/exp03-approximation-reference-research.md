# EXP-03 approximation reference research

Date: 2026-10-29. Scope: local-source research for issue #99. This note identifies a bounded first comparison case and the evidence its set relations can support. It is not a benchmark result, approval to run one, or a historical replay.

## Recommendation

Use the existing `TwoPointsOnParallelLines` finite-game report as the application case, with projected convex-hull references for its `(x1,x2)` and `(x3,x4)` phase planes. The finite dynamics are replayed exactly on the integer lattice, but conversion to binary64 happens while constructing the native 4D V input, before projection. Treat the hull of the stored binary64 projections as the adapter comparison reference and check exact rational lattice inclusion separately; do not label the binary64 result as the mathematical rational hull. A small diamond may remain as a primitive adapter/oracle smoke, but it is not a substitute for the reachability/minimax application example.

The diamond remains a compact adapter check already present in `reports/algorithm-results/approximation-matched-pilot-20261023-r1/input.txt`: vertices `(0,2),(2,0),(0,-2),(-2,0)`, area 8, H description `|x|+|y|<=2`, and equivalent centered zonotope generators `(1,1),(1,-1)`. Its existing pilot is exploratory and must not be promoted into a complete comparison artifact.

For each environment-derived phase-plane projection, the relation matrix can include the exact V-polytope reference, axis box, rotated parallelotope, a zonotope axis-cover when an equivalent projected zonotope is available, and directional ellipsoid. The supported producers are bounded 2D paths; preserve refusals and unsupported routes. Inner approximations should be omitted unless an implementation returns a set whose realizable points and complete inclusion are independently established.

## What the current sources establish

- `docs/architecture/comparison-program.md` (the #99/#100 program contract) requires a complete independent inclusion oracle for guaranteed claims. Volume, sampled supports, residuals, or producer self-report do not prove inclusion. Outcomes must distinguish verified, incorrect, and inconclusive. It names APP-01 #24, APP-02 #33, APP-03 #42, APP-04 #34 and GEO-08 #52 as prerequisites, with #100 as the independent contract-test ticket.
- `docs/architecture/set-representations-and-ellipsoidal-toolbox.md` separates mathematical closure from registered native routes. Plain zonotopes are closed under affine image, projection and Minkowski sum in exact real arithmetic; a general intersection is not a zonotope. Generator reduction is exact only with a redundancy proof, otherwise it needs a declared enclosure direction. Current generator handles have no registered support, containment, intersection or projection route. Constrained zonotopes preserve more operations mathematically, but current registrations do not provide their inclusion oracle either.
- `src/geometry/approximation/zonotope.cpp` exposes zero-column removal as equivalence for unconstrained generators, and `csl.geometry.zonotope.axis-cover` as **outer only**. The cover retains selected factor columns and replaces omitted factor contributions by coordinate-axis radii computed using exact dyadic accumulation and outward binary64 conversion. It explicitly relaxes dependencies; it does not claim realizability, an inner relation, validated prior model arithmetic, or a global error bound. Constrained factors are not a basis for inferring plain-zonotope behavior.
- `reports/algorithm-results/approximation-matched-pilot-20261023-r1/README.md` is a saved descriptive diamond pilot. It reports exact polygon hull equality, exact returned H-row checks for the box and parallelotope, and an admitted axis-cover enclosure for the zonotope. On this fixture the parallelotope area ratio is 1, box and zonotope cover ratios are 2, and ellipsoid ratio is π. Its README explicitly limits admission to the bounded finite input and native output forms; the pilot is preliminary, not the full #99/#100 comparison, and its passing rows are not global inclusion verification.
- `docs/contracts/bounded-hull-checker.md` defines a complete exact dyadic oracle for finite 2D source-index hull outputs, with all-input containment and concrete counterexamples. It is specifically a hull checker, not a generic set-to-set oracle for ellipses or zonotopes. It is a useful proof pattern but cannot be relabelled as the missing universal inclusion oracle.
- `docs/contracts/ellipsoidal-approximation.md` states the directional ellipsoid's mathematical outer construction and its independent check of every bounded V input vertex against projected bounds. It is numerical assurance on stored binary64 inputs, not validated rounding of upstream real calculations, and provides no native inner approximation.
- `docs/contracts/core-interfaces.md` lists registered box/parallelotope and inner-box/inner-parallelotope routes for supported bounded forms, with exact stored-binary64 vertex/ray or H-row inclusion checks. Route scope and assurance are limited; this does not create a general exact-arithmetic inclusion API.

## R29 lead: useful model shape, not an approximation-comparison baseline

R29 is Shorikov and Kalev, “Reachable set computation for solving fuel consumption terminal control problem using zonotopes,” CEUR Workshop Proceedings Vol. 1825, pp. 103–110 (2017 proceedings; conference in 2016), [paper PDF](https://ceur-ws.org/Vol-1825/p13.pdf). `docs/research/zonotope-paper-input-audit.md` identifies the local archived PDF as A21 and editable TeX as A22, gives both SHA-256 values, and records the source locations. The paper's fuel example has four states, 16 transitions, scalar `u(t)` with `|u(t)|<=1`, and an initial zonotope. The archived audit and `docs/research/r29-corrected-scalar-reference.md` derive a dimensionally consistent *inferred* input interpretation: `P(t)=Z(0,[1])`; the paper instead prints four-component control-set data alongside scalar control and a `4x1` input matrix. Algorithm 1 also prints `Ac2` at a control-image center where dimensions and the stated recurrence require `Bc2`.

The corrected scalar reference propagates an exact-rational, unreduced zonotope and has a 20-factor terminal representation after 16 independent control factors. Its saved record and native replay check stage centers, factors and coordinate intervals. These checks establish that separately named corrected reference case, not what historical code ran. R29 has no stated terminal target/objective sufficient for the requested complete inclusion comparison among exact and approximate representations, and the fuel reach set is 4D while the proposed comparison needs a compact complete oracle and illustrative projections. Projecting a zonotope can be exact mathematically, but the current generator API does not register projection or support/containment for generator handles. A 2D plotted projection alone cannot establish 4D inclusion.

Therefore R29 is a follow-on article-derived case, useful for demonstrating generator propagation and later approximation at intermediate horizons, once each projection and the full-dimensional relation checker are implemented. It cannot currently support inner claims: the available R29 propagation is exact only for the inferred input model, while the reduction adapter provides outer covers only. Nor should its corrected reference record be described as historical replay or treated as evidence that an approximate reachable tube bounds the historical run.

## Evidence boundary and next fixture

For the diamond fixture, a complete finite-polytope oracle can be small and exact: check every exact source vertex belongs to the candidate outer set, and check every candidate vertex belongs to the exact source for equivalence/inner claims. For the supported H outputs, exact dyadic evaluation of each half-space on each vertex is complete. For a zonotope output, checking all its `2^m` corners is complete only for a small unconstrained generator count and exact represented dyadic coefficients; convexity then covers the whole zonotope. For an ellipsoid, use its exact quadratic form / projected bound certificate rather than finite point sampling; the adapter-specific certificate must itself be independently validated. Set comparisons involving intersections, constrained factors, unbounded sets or high generator counts remain inconclusive until a sound complete oracle is available.

The existing diamond pilot uses stored-binary64 admission and must not be promoted into a claim about arbitrary real input computations. The environment comparison should bind both the exact integer state nodes and the serialized binary64 point inputs, identify the adapter reference as the convex hull of stored binary64 projections (not the discrete nodes or exact rational projected hull), retain each producer's requested relation and output budget, verify the relation independently after timing, and report rational-lattice inclusion separately from binary64-reference inclusion and descriptive area/support diagnostics. The independent checker should use exact dyadic values for the saved binary64 vertices and exact rational coordinates for lattice points; upstream model arithmetic remains numerical and is not retroactively certified.

## Application case selected from the RL environments

For the reachability/minimax application figure, use the already implemented `TwoPointsOnParallelLines` environment slice from issue #717 rather than the fuel task. Its source-derived four-state map, three-stage finite action adaptation, fixed-plan minimax result, finite-state feedback reachability, forward reachable polytopes, backward-winning intersections, and independently replayed paths are already retained in `reports/algorithm-results/env717-two-points-pilot-v1/` and `env717-two-points-feedback-v1/`. Its two plots have the requested phase-plane coordinates `(x1,x2)` and `(x3,x4)`.

The report explicitly adapts the upstream continuous-control 10-second RL setup to a three-stage finite control/disturbance game. Keep that limitation visible; it is not an RL reproduction or a continuous-control optimality result. The approximation comparison applies current bounded planar producers to native binary64 projections of selected 4D reachable sets. In that case every containment statement is about the corresponding 2D binary64 reference only; exact rational lattice inclusion is a separate diagnostic. Verify the projected relation with a complete independent oracle, and do not infer 4D inclusion from the figures. The diamond remains useful as a small adapter/oracle check, not as the main reachability/minimax demonstration.
