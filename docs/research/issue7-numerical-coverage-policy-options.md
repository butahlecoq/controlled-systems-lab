# Issue #7: scientific numerical-coverage policy options

Date: 2026-10-18. Scope: decision support for the first-profile numerical evidence required by the core architecture. This report compares policy choices; it does not select a scientific guarantee, numeric tolerance, or implementation on the owner’s behalf. No code, solver, build, test, or benchmark was run for this report.

## Why this is an architecture gate

The initial architecture selects nominal optimal control planning with continuous actions and asks for a representation of **all** optimal plans, consistent trajectories, and feasibility/optimality evidence. The result contract defines the joint feasible relation `F`, optimum `v*`, and family `Z* = {z in F : phi(x_T)=v*}`; a single optimizer point or stagewise marginals do not represent that relation. The architecture also distinguishes termination, feasibility, and optimality, and says numerical and validated/certificate-based verification contracts are separate, with numerical verification implemented first. These are project requirements, not findings newly selected here. [Project architecture: modular algorithms and solution families, dated 2026-10-11](../architecture/modular-algorithms-and-solution-sets.md); [initial architecture, dated 2026-10-11](../architecture/initial-architecture.md).

An architecture acceptance decision needs to say what mathematical object numbers denote, what the solver’s success status establishes, what a consumer can independently verify, and when the result must say “unknown/undetermined.” Otherwise a backend’s status string or tolerance silently becomes the system-wide scientific policy. HiGHS itself exposes separate primal/dual statuses, residuals, relative and absolute infeasibilities, and complementarity measures; its guide explains that basic and nonbasic solution routes use different KKT checks and that an apparent optimal result can be downgraded to unknown. [HiGHS `HighsInfo` reference, current source documentation](https://github.com/ERGO-Code/HiGHS/blob/master/docs/src/structures/structs/HighsInfo.md); [HiGHS KKT guide, current source documentation](https://github.com/ERGO-Code/HiGHS/blob/master/docs/src/guide/kkt.md).

## Existing decisions and hard boundary (baseline, not a new proposal)

The report is subordinate to the existing [mathematical-operation compatibility design, sections 3–8](../superpowers/specs/2026-10-13-mathematical-operation-compatibility-design.md). That design already distinguishes set relation from evidence strength, composes support through ordered operation lineage, defines the first-profile module seams, and requires the `OptimalFamilyBuilder` to separate complete, partial, and candidate output. It says numerical evidence does not imply validated support and a residual or low error alone does not establish equivalence or inclusion. The options below address choices that remain open within that design; they are not a replacement specification.

The existing [complete-family verifier seam blocker](../contracts/complete-family-verifier-seam-blocker.md) is authoritative on implementation status: production has **profile-specific analytic verifiers for T-S01 and T-S02 only**. Those verifiers check their canonical frozen problems, relations, optimum claims and bounds. They are not a generic numerical coverage procedure for arbitrary supported problems or Strategy A/B outputs. No generic coverage policy, generic arithmetic/rounding model, numerical tolerance values, or acceptance thresholds are approved. `NumericalCoverageEvidence` is only a typed payload proposal; a residual, tolerance check, solver status, or witness list is not proof that every optimal history is included. A new profile must fail closed for complete-family publication until its own reviewed coverage procedure and compiled verifier exist.

The [terminal-minimizer relation dossier](terminal-minimizer-relations.md) gives exact-arithmetic characterizations for linear, PSD quadratic, and affine residual-norm objectives, and records why a binary64 optimizer anchor and numerical diagnostics do not establish the premise that the point is a true global optimizer. These derivations can inform candidate family construction, but they do not establish numerical coverage. Its dedicated analytic providers/tests and real HiGHS integration cases are profile-specific tests; they do not generalize the T-S01/T-S02 production verification boundary.

Accordingly this report compares *decision options and consequences* for any future first-profile claim. It does not authorize publishing a numerically “complete” family, upgrade existing verifier scope, or propose that generic policy exists. Issue #7 acceptance should name the remaining owner/scientific decisions and preserve the blocker until an admitted profile has a reviewed theorem/procedure and verifier as specified by the blocker record.
## 1. Meaning of numeric input

For a decimal-authored coefficient such as `0.1`, the intended real decimal and the stored binary floating-point value are different mathematical objects. IEEE 754 specifies floating-point formats, arithmetic, exceptions and conversions; C++’s `numeric_limits` reports whether a type matches IEC 60559, so the language type alone is not a proof that every build/operation follows a particular binary64 execution model. [IEEE Std 754-2019, active standard, published 2019-07-22](https://standards.ieee.org/ieee/754/6210/); [ISO C++ draft N4860, C++20 working draft, `numeric_limits::is_iec559`](https://isocpp.org/files/papers/N4860.pdf).

| Policy option | Meaning and evidence obligation | Consequence for first-profile architecture |
|---|---|---|
| **Authored-real semantics** | Input is an intended real model, with a representation/uncertainty relation that binds authored values to stored values. Every numerical claim about the authored model must include a justified input-conversion/model-error enclosure. | Physically meaningful but cannot be inferred from binary64 bytes alone. Requires an authored-number convention (e.g. decimal literals as exact rationals or declared intervals) and propagation of coefficient/input uncertainty into feasibility and objective claims. |
| **Represented-dyadic semantics** | Each finite binary64 datum denotes its exact dyadic rational value; claims concern that encoded model. Record dtype, finite-value restrictions, and any arithmetic assumptions. This gives an unambiguous source problem without pretending that prior physical intent is known. | Simpler, reproducible reference model and compatible with exact rational checking of stored coefficients. Numerical floating-point solve still needs residual/certificate evidence. Does not bound deviation from a pre-rounding physical/authored model. |
| **Two-layer contract** | Preserve the authored input separately, define the represented model exactly, and attach an explicit conversion/uncertainty set where known. Report conclusions at both layers only when the bridge is certified. | Strongest traceability; larger schema and proof burden. If uncertainty is absent, publish represented-model claims only and leave authored-model claims undetermined. |

The existing GEO-02 review demonstrates why this distinction affects geometry: stored dyadic inputs and finite output vertices can be compared exactly after computation, but that does not by itself show that generated outputs equal a pre-rounding real physical model; conversion paths can also lack a global coverage certificate. [GEO-02 floating-model audit, 2026-10-16](geo02-floating-model-audit.md); upstream Qhull’s precision note describes floating-point precision handling and possible “thick” facets, rather than asserting a universal exact equivalence result. [Qhull 8.0.2 precision/imprecision manual](https://www.qhull.org/html/qh-impre.htm).

**Unresolved owner/scientific decision:** For the first profile, are published claims about (a) exact dyadic values represented by the input files, (b) the authored real quantities, or (c) both with a certified bridge? The answer determines serialization, hash identity, unit/conversion metadata, objective recomputation, and what independent checks must consume.

## 2. Assurance level: numerical evidence versus exact/validated evidence

| Assurance option | What it can support | Limits / cost |
|---|---|---|
| **Numerical diagnostics** | Solver-provided primal/dual feasibility statuses, residuals, objective values, gaps, scaling, algorithm and tolerances. Independent recomputation in original coordinates can catch mapping/reporting errors. | Floating-point residuals and solver status are approximate evidence, not automatically a proof of exact feasibility, global optimality, or completeness. Diagnostics require declared units, norm, normalization and tolerances. |
| **Exact certificate for represented data** | Independently checked rational/arithmetic proof for a supported claim, e.g. a feasible primal/dual LP pair proving LP optimality over represented rational data, or a finite branch-and-bound certificate. | Exact checks apply to their precisely declared data and claim. They can be costly and are not available for every solver/model class; a certificate for an objective value need not certify extraction of the complete optimizer relation. |
| **Validated numerical enclosure** | Outward-rounded interval or other rigorous enclosure establishes a bounded error/feasibility/objective interval under a stated arithmetic and model. May prove a gap within an explicit requested bound without exact point recovery. | Requires interval/rounding assumptions and proof obligations through all transformations. “High precision” alone is not validated arithmetic. Enclosures may be too wide to decide a boundary case. |
| **Tiered assurance** | Return numerical candidates by default with an explicit assurance level; optionally upgrade individual claims using exact or validated checking. | Requires result contracts to distinguish a failed check from an unavailable checker and from a mathematical negative result. |

Research and implementation sources establish that this is a real tradeoff, not only a matter of solver configuration: exact rational LP approaches can certify feasibility and safe objective bounds; exact MIP solvers can generate independently checkable optimality certificates; modern research also studies translating floating-point solver answers into exact derivations. [Althaus & Dumitriu, “Certifying feasibility and objective value of linear programs,” *Operations Research Letters* 40(4), 2012, pp. 292–297, DOI 10.1016/j.orl.2012.03.004](https://www.sciencedirect.com/science/article/pii/S0167637712000272); [Cheung, Gleixner & Steffy, “Verifying Integer Programming Results,” 2016, revised 2019, arXiv:1611.08832](https://arxiv.org/abs/1611.08832); [Szeider, “VIPR Certificate Construction from Black-Box ILP Solvers,” CP 2026, LIPIcs 379, paper 52](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.CP.2026.52). These sources concern LP/MILP claims and do not automatically certify this project’s continuous optimal-family extraction.

**Unresolved decision:** Is the first-profile acceptance criterion a clearly labeled numerical optimum candidate plus residual/gap evidence, or must specified scenarios have exact/validated evidence? Which claims (feasibility, value, global optimality, complete family, or authored-model correspondence) require each level? Existing architecture explicitly says numerical first, validated/certificate-based contract retained, but it does not settle which claims numerical evidence suffices for.

## 3. Residuals, optimality conditions, and scaling

For a standard LP `min cᵀx` subject to `Ax=b`, `Gx≤h`, with bounds, a reviewable numerical profile should not store an unexplained single “residual.” At minimum it should identify the tested primal equations/inequalities/bounds, dual stationarity/feasibility equations, complementarity terms, and the primal/dual objective difference or gap when applicable. For convex QP/conic formulations, the strategy must declare and independently evaluate the relevant KKT conditions or valid bound/gap certificate, including any reformulation from the user’s original objective. These are different quantities and can fail independently. The Boyd–Vandenberghe convex optimization text derives KKT conditions and the primal-dual framework for convex problems; HiGHS documents concrete distinct primal/dual residuals and infeasibilities for LP/QP workflows. [Boyd & Vandenberghe, *Convex Optimization*, Cambridge University Press, 2004, chapters 5 and 10](https://stanford.edu/~boyd/cvxbook/bv_cvxbook.pdf); [HiGHS `HighsInfo`](https://github.com/ERGO-Code/HiGHS/blob/master/docs/src/structures/structs/HighsInfo.md); [HiGHS KKT guide](https://github.com/ERGO-Code/HiGHS/blob/master/docs/src/guide/kkt.md).

A useful evidence tuple is `(quantity, norm, original-or-scaled coordinates, absolute value, relative value, normalization denominator, threshold, arithmetic/precision, check implementation, validity)`. Preserve both solver-space and original-problem-space checks where presolve, scaling, variable substitution, objective rescaling, or terminal-state projection occurs. A small normalized residual is evidence under that exact normalization, not a unit-independent physical guarantee.

Scaling choice comparison:

- **Absolute residual only** is easy to interpret in selected units but changes meaning when coordinates/units change. Gurobi’s official guide states its primal/dual feasibility tolerances are absolute and recommends accounting for this in variable and constraint units. [Gurobi Optimizer Reference Manual, current online numerical guide](https://docs.gurobi.com/projects/optimizer/en/current/concepts/numericguide/tolerances_scaling.html).
- **Relative residual only** better reflects magnitude but can hide behavior around zero or depend on a poor denominator. HiGHS reports relative and absolute measures separately; its KKT guide warns that its chosen scale for active components can be smaller than full `||b||`/`||c||`, affecting whether relative tests pass. [HiGHS KKT guide](https://github.com/ERGO-Code/HiGHS/blob/master/docs/src/guide/kkt.md).
- **Paired absolute and relative residuals**, with named norms and denominators, supports diagnosis across scale ranges but requires a policy for zero denominators and interpretation across unit systems. A condition estimate or backward-error measure may be useful diagnostic metadata, but is not a replacement for forward error or a correctness certificate.

**Unresolved decision:** Which norms and denominators are required at the system boundary? Which units/scales are normalized, retained, and reported? Are raw original-coordinate residuals mandatory even if the backend supplies scaled metrics? What solver-reported gap threshold and independent recomputation policy is appropriate to the actual B04-sized first profile? No universal numeric threshold is endorsed by the cited solver manuals; choosing one requires scenario magnitude/units and scientific error tolerance.

## 4. Coverage and completeness of the optimal family

The product-level mathematical target is a relation/set, not just an optimal scalar or one witness. For terminal-only cost, the current contract first forms the full terminal minimizer set and then retains every feasible trajectory ending in it. A representation is complete only if it describes that entire set under the declared assurance semantics. Sampling points, vertex lists, solver basis, a single optimal trajectory, or per-stage marginals can establish witnesses or diagnostics, but cannot alone establish there are no other optima. The project’s own contract provides a two-stage example where optimal controls satisfy `u0+u1=1`: each marginal is `[0,1]`, while the Cartesian product admits nonoptimal plans. [Modular algorithms and optimal solution families, section “What constitutes the result”](../architecture/modular-algorithms-and-solution-sets.md).

Possible coverage mechanisms and their implications:

| Mechanism | Potential completeness evidence | First-profile fit / caveat |
|---|---|---|
| **Explicit parametric/polyhedral relation** | Give defining constraints plus mapping back to original states/controls; independently verify that it is exactly the feasible optimal face/set, or provide validated enclosure with explicit semantics. | Natural for linear/polyhedral supported cases; scaling, degeneracy, projection, and conversion still need verification. A solver basis/active set alone is not a full projected family. |
| **Finite enumeration with proof of exhaustive search** | Enumerate all alternatives and retain a checkable search/certificate that every branch was covered and every retained optimum is tied at the certified optimum. | Applies only when the relevant choice set is finite or finite branching is complete; does not make continuous within-branch families finite. |
| **Oracle/implicit set representation** | Provide exact/validated membership/witness behavior plus a proof that the oracle’s defined set equals the optimizer set. | May avoid materializing large families; callers need query semantics and assurance guarantees, not just an opaque handle. |
| **Sampled or approximate family** | State a sampling/covering or Hausdorff/error guarantee with a proved bound and declare approximation direction. | Useful only as an explicitly approximate request/result; must not be labeled the complete exact optimal family by default. |

Optimal-family completeness has at least two independent parts: (1) soundness, every included plan is feasible and optimal to the stated assurance level; (2) coverage, every plan in the mathematical optimal set is represented, or the result supplies a rigorous outer/inner approximation with named direction/error. A sound finite witness set may be incomplete; a feasible tube may cover suboptimal plans. A scalar objective gap does not on its own prove family coverage.

**Unresolved decision:** For the first supported continuous/polyhedral class, which families must be returned as explicit constraints, and which representations are allowed as equivalent implicit relations? What independently checked evidence suffices for both soundness and coverage after projection back to controls? Are approximate family requests excluded from v1 or supported with explicitly requested error/direction? These decisions bind algorithm modularity, result serialization, query methods, and what “all optimal plans” means operationally.

## 5. Unsupported, undetermined, and failed outcomes

Do not collapse mathematical status, algorithm capability, and evidence availability. A useful result state separates:

1. **Problem disposition:** feasible optimum attained; infeasible; objective unbounded; finite infimum not attained (if supported inputs allow it); or unsupported model/objective/domain/representation.
2. **Run termination:** completed; iteration/resource/deadline limit; cancelled; numerical failure; backend error.
3. **Evidence disposition per claim:** established at named numerical/exact/validated tier; contradicted by a checked counterexample; unknown/undetermined because evidence is insufficient; unavailable/not attempted; or checker failure.

HiGHS’ KKT guide says it can reduce a nominal “optimal” status to “unknown” when additional residual checks fail; its info structure separates primal and dual solution availability and metrics. This supports an explicit unknown/undetermined status rather than converting uncertainty into success/failure. [HiGHS KKT guide](https://github.com/ERGO-Code/HiGHS/blob/master/docs/src/guide/kkt.md); [HiGHS `HighsInfo`](https://github.com/ERGO-Code/HiGHS/blob/master/docs/src/structures/structs/HighsInfo.md).

**Undetermined** should mean the run does not establish the requested claim: e.g. a candidate exists but original-coordinate feasibility cannot be decided at the requested tolerance; a numerical solve reports a possible optimum but no gap/certificate can distinguish near ties; coverage extraction is incomplete; or authored-real conversion error is unknown. It must preserve available candidates and diagnostics without upgrading their claim. **Unsupported** means the declared strategy does not claim to handle that request; it should be detectable before silently applying a weaker formulation. **Numerical failure** records the attempt and does not imply infeasibility. A tighter tolerance attempt that fails to converge should not be relabeled as proof of no solution.

This split matches the project’s current separation of termination, feasibility, and optimality plus its explicit distinction among unsupported, unbounded, unattained and infeasible requests. [Modular algorithms and optimal solution families](../architecture/modular-algorithms-and-solution-sets.md); [initial architecture result contracts](../architecture/initial-architecture.md).

**Unresolved decision:** Which statuses are stable public enum values and which are per-claim evidence statuses? When can an accepted result be “numerically optimal” without a validated proof, and should the unqualified word `optimal` be reserved for exact/validated evidence? Which partial payloads survive unsupported, timeout, numerical failure, or undetermined coverage?

## 6. Precision and tolerance policy

| Choice | Advantages | Risks / obligations |
|---|---|---|
| **Fixed binary64 defaults** | Lowest API/setup burden; maps to common solver defaults and existing integrations. | Absolute solver tolerances are unit-dependent; defaults are backend-specific, not a domain guarantee. Record backend/version/effective settings and independently recompute checks. |
| **User-declared tolerances per problem** | Makes requested error/feasibility accuracy explicit and supports domain scales. | Validate consistency and units; solver may not honor a target or may need iterative refinement/higher precision. Return achieved bounds, never only requested values. |
| **Scale-aware tolerances** | Tie acceptance to named normalized residuals and model scale. | Definition of scale and zero behavior becomes part of mathematical contract; solver relative criteria may use different normalization. |
| **Escalation policy (double → higher precision/exact/validated checker)** | Uses expensive assurance selectively near boundaries or for acceptance-critical cases. | Must be deterministic/auditable, budgeted, and return undetermined when escalation cannot decide. Higher precision alone is not proof unless rounding/error is bounded or final checks are exact. |

Gurobi documents default primal and dual feasibility tolerances of `1e-6`, emphasizes that they are absolute, and shows how small coefficient gaps can make numerical feasibility conclusions ambiguous. This is evidence that defaults are solver behavior, not a portable physical policy. HiGHS’ official current docs likewise expose separate absolute and relative residual/infeasibility settings and status logic. The deployed integration should pin and report the actual HiGHS version/options rather than infer policy from current online `master` documentation. [Gurobi numerical guide, current online manual](https://docs.gurobi.com/projects/optimizer/en/current/concepts/numericguide/tolerances_scaling.html); [HiGHS `HighsInfo`, current source docs](https://github.com/ERGO-Code/HiGHS/blob/master/docs/src/structures/structs/HighsInfo.md); [HiGHS KKT guide, current source docs](https://github.com/ERGO-Code/HiGHS/blob/master/docs/src/guide/kkt.md).

A result should retain requested and effective precision, all feasibility/optimality tolerances, scaling and presolve configuration, arithmetic type, solver version/build, status, residual values and norms, objective primal/dual values or valid bounds, and independent-check results. If a backend omits a metric or does not expose a primal/dual solution, represent it as unavailable; do not fabricate zero or assume optimal status implies every check was performed. The public result should distinguish *requested tolerance*, *backend stopping threshold*, *independent acceptance threshold*, and *observed error/residual*.

**Unresolved decision:** Should numerical acceptance use one set of profile constants, model-declared normalized tolerances, or both? Which problems require escalation? Are tolerance values pinned globally, per quantity, per solver, or per scenario? Scientific owners must define tolerable constraint violation and objective uncertainty in problem units; backend defaults cannot answer that.

## 7. Minimum issue #7 decision record before architecture acceptance

The reviewer can treat this as the outstanding policy checklist. Issue #7 need not require one exact solver or all assurance implementations to close architecture acceptance, but it should require explicit owners’ decisions and a contract that makes the implementation’s present guarantee truthful:

1. **Model semantics:** declare represented-dyadic, authored-real with input bounds, or two-layer semantics; state number parsing/conversion and the scope of each claim.
2. **Assurance vocabulary:** distinguish numerical diagnostics from exact and validated evidence; define which claim may carry each label and how an independent checker relates to the solver.
3. **Residual contract:** name primal/dual/KKT/complementarity/gap quantities, coordinate space, norms, scaling, normalization, and requested/effective/acceptance tolerances; retain raw original-space checks.
4. **Family contract:** require soundness and coverage separately; identify the supported first-profile family representation and how its full coverage is established; do not infer completeness from point sampling, one basis, one witness or marginals.
5. **Outcome contract:** separate problem disposition, run termination and evidence disposition; preserve unsupported and undetermined outcomes and partial evidence.
6. **Precision/reproducibility:** pin backend version and effective configuration in result evidence; define when a second precision/checking tier is required and how non-decision terminates.
7. **Scientific owner decisions:** name who approves units/scales, acceptable original-model violations/objective gaps, input conversion bounds, and the allowed meaning of “optimal” for the first profile.

The current sources establish why these decisions matter and show established alternatives; they do not determine acceptable physical errors, the first-profile tolerance values, whether represented data suffices for science claims, or which family extractor is complete for this product. Those remain explicit owner/scientific decisions. This report therefore does not declare issue #7 or any numerical coverage gate satisfied.
