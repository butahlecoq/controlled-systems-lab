# Cross-cutting API decisions (proposal)

**Status: proposed defaults for owner review.** These choices make the class map implementable without closing any scientific-profile, assurance, or resource-policy decision on the owner's behalf. They refine the seams in the [class-level architecture](2026-10-12-class-level-system-architecture.md); they do not authorize implementation or change existing ticket scope.

## Decision status and recommended v1 path

The owner has approved continuous controls with the working scenario bound `u ∈ [-1, 1]`. Treat this as an explicit assumption for new baseline scenarios; it does not restore or verify the historical B04 bound or any other missing archival input. The class map's remaining `nominal_open_loop` profile (known deterministic initial point, affine discrete stages, absent/zero disturbance, and no new state or temporal coupling restrictions) is the proposed first scientific profile; data types that represent more general systems do not imply solver support.

| Decision | Recommended v1 default | Still open / alternatives | Rationale |
|---|---|---|---|
| First scenario and control domain | Use the owner-approved `u ∈ [-1, 1]` in explicitly identified baseline scenario files. Keep historical B04 unavailable until its canonical source values are restored. | Whether any future archival reconstruction uses a different bound or convention. | Enables a concrete baseline without rewriting historical evidence. |
| Family outcome and assurance | Use the closed family outcome below. Start with `NumericalToleranceSupport` and report its arithmetic, tolerances, method, coverage procedure, and diagnostics. A claim requiring validated completeness is unsupported until a compatible certificate verifier exists. | Which objective profiles and numerical acceptance thresholds are admitted; whether/when validated arithmetic is required. | Keeps the requested whole optimal family distinct from a witness list while preventing floating-point residuals from being described as exact proof. |
| Geometry planning | Compose the existing registrations through one side-effect-free planner; admit only operation-specific plans whose composed guarantee satisfies the request. A full-family path uses exact/equivalent mathematical operations, with numerical assurance stated separately. | Initial representations, operation/capacity fixtures, and any separately proved weaker-plan theorem. | Prevents a convenient approximation fallback from silently weakening the complete-family target. |
| Execution and parallelism | Run algorithms serially within one task. Let the outer executor own concurrency across independent scenarios/comparison tasks under one shared budget. In a paired timing experiment, interleave strategies but run timed repetitions without competing tasks. | Worker caps, deadlines, memory policy, and later internal fan-out. | Avoids nested oversubscription and reduces timing contamination while leaving task-level parallel scaling available. |

For the initial portable artifact, store the canonical run records alongside the comparison manifest; a later immutable external store may implement the same references. | Encoding/schema version and the future storage adapter. | A self-contained first artifact is easy to archive and verify; content-addressed references permit deduplication and external storage later without changing comparison identity. |
| Reporting and timing | Persist raw per-run records and observations first. These are recommendations for review, not additional owner approvals. The approved control bound is the only new modeling choice fixed here; scientific profile, assurance threshold, geometry fixtures, resource values, and publication/storage infrastructure remain open as shown above.

## 1. Optimal-family result and evidence

**Proposed default:** represent family results with a closed outcome variant, not an envelope whose target and evidence fields can be freely combined:

```cpp
struct CompleteOptimalFamily {
  JointRelation relation;
  OptimumEvidence optimum;
  CompletenessEvidence completeness;
};
struct PartialOptimalFamily {
  JointRelation relation;
  OptimumEvidence optimum;
  CoverageScope known_scope;
};
using FamilyRelationToTarget = std::variant<OuterCandidateEvidence,
    InnerSubsetEvidence, HeuristicRelationEvidence>;
struct CandidateFamily {
  JointRelation relation;
  FamilyRelationToTarget relation_to_target;
};
using OptimalFamilyOutcome = std::variant<CompleteOptimalFamily,
    PartialOptimalFamily, CandidateFamily>;
using SynthesisOutcome = std::variant<OptimalFamilyOutcome, Infeasible,
    Unbounded, UnattainedInfimum, Unsupported, Cancelled>;
```

The complete variant therefore always carries a relation, optimum evidence, and completeness evidence. Partial results state their known coverage; candidate results state the relation to the true target. A witness query may return a witness and feasibility evidence, but cannot upgrade the family outcome or completeness claim. Evidence is bound to the resolved-problem digest, objective digest, request/profile digest, ordered relation coordinates, strategy and version, and every transformation used to obtain the relation. Those identities are immutable values, not display labels. Evidence uses the class-map assurance vocabulary: `NumericalToleranceSupport` records arithmetic, tolerances, coverage procedure, and diagnostics supporting a numerical claim; `ValidatedCompletenessCertificate` is reserved for a checked certificate under an explicitly supported validated arithmetic/model profile. Numerical tolerance support is not exact set equality or validated completeness, and cannot satisfy a request requiring a `ValidatedCompletenessCertificate`. Any future certified or exact mechanism must map explicitly to one of these assurance levels and be checked by a supported verifier; it does not add a competing `ValidatedClaim` or `CertifiedClaim` variant.

The API should make mismatched bindings difficult to construct: carry `ResolvedProblemDigest`, `ObjectiveDigest`, `EffectiveFamilyRequestDigest`, ordered `JointCoordinateSchemaId`, `StrategyVersion`, and ordered `TransformStepIdentity` lineage in the evidence binding, followed by a typed `CompletenessAssurance`. At the result boundary, require exact identity and coordinate agreement with the owning `PreparedStrategy` and request, and require the trace to compose from that strategy's resolved problem. The independent verifier checks numerical-support claims against the original resolved problem. Type shape and digest binding make provenance auditable; neither alone proves the mathematical claim. `CompleteOptimalFamily` is a claim at its explicitly declared assurance level, not a promise of exact set equality in binary64. It may be produced only by a strategy/verifier path with a checkable coverage argument; a numerical tolerance check alone is not that argument.

Keep the relation payload behind `JointRelationPayload`; add query capabilities through typed relation adapters rather than exposing representation-specific storage through `OptimalFamilyOutcome`. A witness query may return a feasible witness but cannot upgrade the source family outcome. Reject unsupported queries and unsupported assurance requests explicitly. Cancellation, deadline expiry, and resource-limit stops use the `Cancelled` terminal outcome with a typed termination reason; any partial relation retained for diagnosis stays partial and is not returned as a complete-family success.

**Class-map seam:** `OptimalFamily`, `JointRelation`, `JointRelationPayload`, `FamilyTarget`, `FamilyEvidence`, `Witness`, and the independent verifier. **Tickets:** [SYN-02 #61](https://github.com/butahlecoq/controlled-systems-lab/issues/61), [SYN-03 #66](https://github.com/butahlecoq/controlled-systems-lab/issues/66), [SYN-04 #67](https://github.com/butahlecoq/controlled-systems-lab/issues/67), [SYN-06 #43](https://github.com/butahlecoq/controlled-systems-lab/issues/43), and shared strategy-boundary outcome enforcement/tests [SYN-07 #155](https://github.com/butahlecoq/controlled-systems-lab/issues/155).

## 2. Nested execution control and provider lifetime

**Proposed v1 default:** one outer-executor-owned `ExecutionContext` supplies cancellation, deadline, numerical policy, and the single `ResourcePolicy` for a strategy and all generated requests. Strategy and algorithm work is serial within one task; the outer executor owns concurrency across independent tasks/scenarios/strategy runs. A future internal-fan-out seam may lend scoped permits from the same budget, but v1 strategies do not create nested executors, independent pools, or reset budgets. In paired timing runs, interleave strategies and avoid overlapping timed repetitions to reduce contention; comparison-level parallelism can be selected outside the timed pair.

The policy and run record distinguish configured, admitted, observed, and enforced facts for thread and memory use. Record requested/effective worker counts, numerical-backend thread settings, and backend-reported or measured use where available; otherwise record `unknown`/`unavailable`. Adapters either apply a supported thread cap or explicitly report it unenforced. Memory estimates or admission checks are not runtime enforcement; never claim a hard limit unless the selected adapter/platform actually enforces it. Exact caps, deadlines, and platform mechanisms remain owner choices.

A prepared provider is owned by the prepared strategy/workspace; it cannot outlive that execution or expose a raw native workspace. Every generated request passes the provider's frozen capability/requirement admission before snapshot or native workspace creation, and retains provider provenance. Each mutable workspace has one task owner. The execution context's stop token and deadline are checked before admission, between generated requests, and at documented long-operation checkpoints inside adapters; an adapter unable to interrupt an in-progress native call reports that limitation and checks immediately after return. Cancellation or a resource-limit stop preserves diagnostics and any partial relation as incomplete, but returns a distinct non-success outcome and cannot satisfy family completeness. Partial work is never silently discarded into an infeasibility result.

This selects execution ownership and truthful accounting without choosing the owner's worker count, memory cap, deadline values, cancellation latency guarantee, or any future internal-permit policy.

**Class-map seam:** `ExecutionContext`, `ResourcePolicy`, `PreparedStrategy`, `SynthesisWorkspace`, `PreparedProvider`, and generated-request admission. Provider admission is implemented by [merged PR #143](https://github.com/butahlecoq/controlled-systems-lab/pull/143); its per-query hull composition is integrated by [merged PR #144](https://github.com/butahlecoq/controlled-systems-lab/pull/144). This hull path does not by itself provide generated-request composition for either full synthesis strategy. **Tickets:** [TEST-15 #78](https://github.com/butahlecoq/controlled-systems-lab/issues/78), plus strategy implementation coverage in [SYN-03 #66](https://github.com/butahlecoq/controlled-systems-lab/issues/66) and [SYN-04 #67](https://github.com/butahlecoq/controlled-systems-lab/issues/67).

## 3. Geometry planning, guarantees, and materialization

**Proposed default:** `GeometryOperationPlanner` composes the existing operation, conversion, and approximation registrations. A `GeometryOperationRequest` states the operation, ordered input representations, optional requested output representation, required guarantee/relation, and capabilities. Each registered operation declares a typed guarantee-transfer rule for its ordered input claims and emits a scoped output claim. Conversion, intersection, projection, image/preimage, and optimization do not share a generic guarantee ordering: a missing transfer rule, incompatible representation, or insufficient composed guarantee rejects the plan before any workspace or materialization begins. The rule is part of the selected adapter contract and provenance, so the verifier can audit the complete plan.

For a complete-family request, every transformation must be exact/equivalent under its declared mathematical semantics unless a separately reviewed theorem establishes that the composed weaker operations still prove the requested coverage. Floating-point evaluation of an exact mathematical operation still carries `NumericalToleranceSupport`, not exact or validated evidence. Inner, outer, and heuristic approximations may run only when explicitly requested and must produce the matching partial/candidate relation; they are never a silent fallback for a complete-family plan. Keep expressions/lazy results where the selected adapter supports the required queries. Full representation conversion is an explicit materialization step, subject to the caller's size/resource budget and cancellation, with representation growth and evidence reported. Sampled support directions remain samples or declared enclosures, never an exact-set claim. Do not create a second operation registry unless concrete composition requirements cannot be expressed by the typed registrations.

For a complete-optimal-family request, the planner must reject any operation plan whose composed geometry guarantee cannot support the requested coverage claim; an inner/outer/heuristic relation may produce a candidate or partial outcome, never be relabelled complete. Each composed step carries input evidence identities and emits scoped output evidence, so a later verifier can audit the chain. The planner describes what registered operations promise; it does not prove the operation implementation correct or validate floating-point arithmetic.

**Class-map seam:** `GeometryPort`, `ConversionPort`, `ApproximationPort`, their request/outcome types, `GeometryOperationPlanner`, and `PreparedGeometryPlan`. **Tickets:** [GEO-02 #40](https://github.com/butahlecoq/controlled-systems-lab/issues/40), [GEO-04 #41](https://github.com/butahlecoq/controlled-systems-lab/issues/41), [GEO-08 #52](https://github.com/butahlecoq/controlled-systems-lab/issues/52), [GEO-03 #31](https://github.com/butahlecoq/controlled-systems-lab/issues/31).

## 4. Immutable comparison definition and run identity

**Proposed default:** separate a caller-authored `ComparisonSpec` from the executed `ComparisonRun`. The spec identifies the resolved problem by content digest; effective strategy/profile and objective request; requested assurance and tolerances; requested outputs/projections and family target; selected strategy/algorithm/backend identities and versions; requested thread/memory policy; and repetition protocol. Its versioned canonical serialization produces a stable `ComparisonSpecId`; edits to any of these values create a new identity. The spec is immutable once execution begins. Requested settings live in the spec; effective settings and observed outcomes live in the corresponding run records.

Each individual strategy execution/repetition produces an immutable, content-addressed `RunRecordRef` that binds the same resolved-problem digest and effective request/profile identity to strategy/algorithm and backend identities/versions, build/configuration identities, effective numerical and resource settings, terminal outcome, assurance evidence, timings, resource observations, and raw measurement payload. The executed `ComparisonRunId` is derived from the `ComparisonSpecId`, the ordered complete set of individual `RunRecordRef` identities (including repetition indices and every terminal outcome), and the comparison schema version. Reruns append new records; they never overwrite a record or reassign an old identity. Thus equal source commits with different measured payloads cannot reuse a report/comparison identity.

Validate before pairing that both runs share the same problem, objective, profile/request, requested assurance, tolerances, output target, and repetition protocol. Record effective backend/config/resource differences explicitly; a required matched-backend comparison rejects mismatches, while an owner-permitted exception becomes a separately labelled comparison and cannot be pooled with matched runs. Preserve failed, unsupported, cancelled, resource-limited, and incomplete attempts alongside successes. Content addressing is over a versioned canonical encoding. V1 publication should put canonical immutable run records and their manifest in a self-contained comparison bundle, while all APIs and rendered links use `RunRecordRef`; a future store adapter may resolve those references externally only if digest verification and portability are preserved.

The execution/observation boundary records module timings and resource observations; the comparison layer aggregates stored records, not live workspaces. Timing records identify the measured phase and whether a span is inclusive of nested spans. Never add inclusive parent and child durations as if they were independent work; report wall time and additive module totals separately, with missing measurements marked unavailable. Correctness/trajectory HTML can be generated from an available run, but a comparative performance summary requires at least five tuned Release repetitions per strategy, alternating strategy order, and a separate limiter profile. The renderer validates identities/schema and renders the persisted family/trajectory data, raw measurements, tables, and explicitly labelled plots; it never calls a solver or recomputes a result. A sample cloud or selected witness plot is not a mathematical projection of the full family.

**Class-map seam:** `ComparisonSpec`, `ComparisonSpecId`, `RunRecordRef`, `ComparisonRun`, and `ComparisonRunId`, plus the saved-record renderer. This API shape refines the class-map comparison artifact decision; it does not decide storage location or publication host. **Tickets:** [OBS-04 #83](https://github.com/butahlecoq/controlled-systems-lab/issues/83), [EXP-02 #94](https://github.com/butahlecoq/controlled-systems-lab/issues/94), and the end-to-end comparison in [SYN-05 #71](https://github.com/butahlecoq/controlled-systems-lab/issues/71).

## Decisions that remain open for the owner

- **Scientific profile (needed before synthesis implementation scope is frozen):** confirm the proposed `nominal_open_loop` assumptions and admitted objective forms. The owner-approved `u ∈ [-1, 1]` baseline is fixed; feedback, uncertain-initial-state quantifiers, hybrid modes, process disturbance, and nonempty temporal coupling remain future profiles. Recommendation: keep v1 at the class-map profile because it makes Strategy A/B comparisons well-defined while model types can still represent broader systems. Hybrid modes, guards, resets, and transitions are a distinct future profile tracked in [EXT-07 #156](https://github.com/butahlecoq/controlled-systems-lab/issues/156).
- **Numerical acceptance contract (needed before a numerical result can be called a complete-family result):** choose/check tolerance fields, arithmetic profile, acceptance thresholds, and the independent checks supporting `NumericalToleranceSupport`. Recommendation: publish the method and diagnostics and use analytic fixtures; never imply validated or exact completeness. A request requiring `ValidatedCompletenessCertificate` must reject until a validated backend/verifier is available.
- **Geometry fixture profile (needed before geometry ticket acceptance):** select first exact/equivalent operation set, dimensions/capacity fixtures, and any approved approximation relation. Recommendation: make the first complete-family path use only operation chains with reviewed transfer rules; test inner/outer approximation separately as candidate/partial output.
- **Runtime values and enforcement (needed before promising hard limits):** set worker/deadline/memory values and decide what limits each selected backend/platform can enforce. Recommendation: keep per-task algorithm serial in v1, schedule independent tasks in the outer executor, and record unknown/unavailable honestly; add permits only if a measured internal parallel workload justifies them.
- **Evidence payload and verification ownership (needed before freezing implementation interfaces):** review the typed binding, numerical/validated assurance payloads, and which verifier creates/checks each field. The closed variants are proposed API shape; they do not prove their evidence correct by construction.
- **Comparison encoding/storage (needed before implementing persistence):** choose the canonical serialization/version and publication integration. Recommendation: ship a self-contained v1 comparison bundle with digest-verified immutable run records; keep `RunRecordRef` storage-agnostic so a later immutable external store can resolve the same identities. Embedding does not mean mutable or source-commit-only identity.
- **Publication details (needed before deploying a public report site):** choose hosting location, plot/export size limits, and any audience/access policy. The report contract already requires saved-data-only rendering, raw run evidence, timing semantics, and explicit plot scope.

These choices do not block revising or reviewing this proposal. The scientific profile, assurance acceptance contract, and exact geometry fixture are the owner inputs that materially determine first synthesis implementation scope; storage/hosting and concrete resource values can be selected later against the proposed stable contracts.
