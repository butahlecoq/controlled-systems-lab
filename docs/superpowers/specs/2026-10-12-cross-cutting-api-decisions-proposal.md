# Cross-cutting API decisions (proposal)

**Status: proposed defaults for owner review.** These choices make the class map implementable without closing any scientific-profile, assurance, or resource-policy decision on the owner's behalf. They refine the seams in the [class-level architecture](2026-10-12-class-level-system-architecture.md); they do not authorize implementation or change existing ticket scope.

## Decision status and recommended v1 path

The owner has approved continuous controls with the working scenario bound `u ∈ [-1, 1]` for new baseline scenarios. The first `nominal_open_loop` profile is also confirmed: known deterministic initial point, affine discrete stages, absent/zero disturbance, and no added state or temporal coupling restrictions. Neither decision restores or verifies historical B04 inputs. Data types that represent more general systems do not imply solver support.

## 1. Optimal-family result and evidence

**Proposed default:** represent family results with a closed outcome variant, not an envelope whose target and evidence fields can be freely combined:

The class map is the canonical C++ type sketch for these outcomes. It defines
`CompleteOptimalFamily`, `PartialOptimalFamily`, `CandidateFamily`, the closed
`OptimalFamilyOutcome`, the opaque `OptimalFamily` handle, and the complete
`SynthesisResult` with scoped stop evidence. Keep those declarations in one
place so candidate-feasibility scope and retained evidence cannot drift between
two nearly identical sketches.

The complete variant always carries a relation, optimum evidence, and completeness evidence. Partial results carry evidence that every retained history is optimal and state their known coverage; candidate results state the relation to the true target and separately scope feasibility. A witness query may return a witness and feasibility evidence, but cannot upgrade the family outcome or completeness claim. Evidence is bound to the resolved-problem digest, effective family request, ordered relation coordinates, strategy and version, and every transformation used to obtain the relation. Those identities are immutable values, not display labels. The class map distinguishes numerical support, which records arithmetic, tolerances, coverage procedure, and diagnostics without proving exact set equality, from validated completeness, which requires a checked certificate under a supported validated arithmetic/model profile. Its proposed payload names are `NumericallySupportedCompleteness` and `ValidatedCompleteness`. The numerical acceptance policy and coverage procedure remain open. Any future exact or certified mechanism must map explicitly to a supported assurance level and verifier; it does not add a competing claim variant.

The API should make mismatched bindings difficult to construct: carry `ResolvedProblemDigest`, `ObjectiveDigest`, `EffectiveFamilyRequestDigest`, ordered `JointCoordinateSchemaId`, `StrategyVersion`, and ordered `TransformStepIdentity` lineage in the evidence binding, followed by a typed `CompletenessAssurance`. At the result boundary, require exact identity and coordinate agreement with the owning `PreparedStrategy` and request, and require the trace to compose from that strategy's resolved problem. The shared publication boundary must validate the evidence type, binding, provenance, and support against the requested assurance before accepting a complete-family claim. The independent verifier checks numerical-support claims against the original resolved problem. Type shape and digest binding make provenance auditable; neither alone proves the mathematical claim. `CompleteOptimalFamily` is a claim at its explicitly declared assurance level, not a promise of exact set equality in binary64. A numerical tolerance check alone is not a coverage argument.

**Current evidence-guard migration gate (#155, #157, T-V02).** The implemented `check_family_evidence` is not safe authorization for complete-family publication. It rejects `NumericalCheck` as completeness support, but an exact-family target under numerical assurance can still pass with `Unestablished`, `SymbolicArgument`, or an unchecked `CertificateReference` after the problem-ID checks. Until the shared strategy boundary and guard are migrated to validate typed support, identity binding, provenance, and scope together, treat complete-family publication as unsupported. Migrate `OptimalFamily`, the request/result contracts, `check_family_evidence`, registry offers/admission, artifact encoding, and callers together. Add public tests that reject unestablished and unverified support and accept only the reviewed positive numerical-evidence fixture; keep validated-assurance rejection and tampered-binding cases. This gate does not choose the scientific coverage procedure, tolerance values, or acceptance thresholds. Those remain subject to owner and reviewer decision.

Keep the relation payload behind `JointRelationPayload`; add query capabilities through typed relation adapters rather than exposing representation-specific storage through `OptimalFamilyOutcome`. A witness query may return a feasible witness but cannot upgrade the source family outcome. Reject unsupported queries and unsupported assurance requests explicitly. `Termination` separates completion, cancellation, resource limit, numerical failure, and generated-request rejection from the mathematical outcome. The `cancelled` termination carries typed stop reasons that distinguish user cancellation from deadline expiry; `resource_limit` remains its own termination. These are execution facts, not mathematical outcomes. `Unsupported` is a pre-solve admission result. A late provider rejection after evidence exists is `operation_rejected` in `SynthesisResult`, carrying request identity, registry-independent rejection diagnostics, completed lineage, and retained-evidence scope. Any partial relation retained for diagnosis stays partial and is not returned as a complete-family success. See the canonical callable contract in the [class-level architecture](2026-10-12-class-level-system-architecture.md).

**Class-map seam:** `OptimalFamily`, `JointRelation`, `JointRelationPayload`, `FamilyTarget`, `FamilyEvidence`, `Witness`, and the independent verifier. **Tickets:** [SYN-02 #61](https://github.com/butahlecoq/controlled-systems-lab/issues/61), [SYN-03 #66](https://github.com/butahlecoq/controlled-systems-lab/issues/66), [SYN-04 #67](https://github.com/butahlecoq/controlled-systems-lab/issues/67), [SYN-06 #43](https://github.com/butahlecoq/controlled-systems-lab/issues/43), and shared strategy-boundary outcome enforcement [SYN-07 #155](https://github.com/butahlecoq/controlled-systems-lab/issues/155), with the independent public-API contract suite [TEST-24 #157](https://github.com/butahlecoq/controlled-systems-lab/issues/157).

## 2. Nested execution control and provider lifetime

**Proposed v1 default:** one outer-executor-owned `ExecutionContext` supplies cancellation, deadline, and the single `ResourcePolicy` for a strategy and all generated requests. The prepared `FamilyRequest.numerical` is authoritative for solve/evidence policy; derive the context's numerical policy from it and reject a mismatch before execution. A separately requested verifier policy has its own identity and cannot rewrite solve evidence. Strategy and algorithm work is serial within one task; the outer executor owns concurrency across independent tasks/scenarios/strategy runs. A future internal-fan-out seam may lend scoped permits from the same budget, but v1 strategies do not create nested executors, independent pools, or reset budgets. In paired timing runs, interleave strategies and avoid overlapping timed repetitions to reduce contention; comparison-level parallelism can be selected outside the timed pair.

The policy and run record distinguish configured, admitted, observed, and enforced facts for thread and memory use. Record requested/effective worker counts, numerical-backend thread settings, and backend-reported or measured use where available; otherwise record `unknown`/`unavailable`. Adapters either apply a supported thread cap or explicitly report it unenforced. Memory estimates or admission checks are not runtime enforcement; never claim a hard limit unless the selected adapter/platform actually enforces it. Exact caps, deadlines, and platform mechanisms remain owner choices.

A `PreparedProvider` owns a frozen registration, requirements, and provenance. It can outlive its source registry and can be copied into a strategy/workspace; the registration callbacks must still obey the documented purity and captured-state lifetime contract. Each generated request passes the provider's frozen capability/requirement admission before snapshot or native workspace creation, and retains provider provenance. Each mutable workspace has one task owner and is destroyed with its owning task. Prepared requests and immutable result handles own their data; borrowed `std::span` values and references remain valid only for the documented call or while their owning handle lives. The execution context's stop token and deadline are checked before admission, between generated requests, and at documented long-operation checkpoints inside adapters; an adapter unable to interrupt an in-progress native call reports that limitation and checks immediately after return. Cancellation or a resource-limit stop preserves diagnostics and any partial relation as incomplete, but returns a distinct non-success outcome and cannot satisfy family completeness. Partial work is never silently discarded into an infeasibility result.

**Migration rule for stop classification:** the current `RegisteredLPQueryRunner` reports a pre-execution deadline as `Termination::resource_limit` while its `LPQueryNotRunReason` records `deadline`. At the proposed synthesis boundary, normalize that provider record into `Termination::cancelled` with the typed `deadline` stop reason. Preserve user cancellation as `cancelled` with its `user_cancel` reason. Reserve `resource_limit` for actual resource-budget exhaustion. The public contract suite in [TEST-24 #157](https://github.com/butahlecoq/controlled-systems-lab/issues/157) must assert that an expired deadline cannot leak the provider's legacy `resource_limit` classification and that resource exhaustion remains distinct.

This selects execution ownership and truthful accounting without choosing the owner's worker count, memory cap, deadline values, cancellation latency guarantee, or any future internal-permit policy.

**Class-map seam:** `ExecutionContext`, `ResourcePolicy`, `PreparedStrategy`, `SynthesisWorkspace`, `PreparedProvider`, and generated-request admission. Provider admission is implemented by [merged PR #143](https://github.com/butahlecoq/controlled-systems-lab/pull/143); its per-query hull composition is integrated by [merged PR #144](https://github.com/butahlecoq/controlled-systems-lab/pull/144). This hull path does not by itself provide generated-request composition for either full synthesis strategy. **Tickets:** [TEST-15 #78](https://github.com/butahlecoq/controlled-systems-lab/issues/78), plus strategy implementation coverage in [SYN-03 #66](https://github.com/butahlecoq/controlled-systems-lab/issues/66) and [SYN-04 #67](https://github.com/butahlecoq/controlled-systems-lab/issues/67).

## 3. Geometry planning, guarantees, and materialization

**Proposed default:** `GeometryOperationPlanner` composes the existing operation, conversion, and approximation registrations. A `GeometryOperationRequest` carries its immutable request identity and a typed `GeometryOperation` payload, including all actual operands: affine matrices/offsets for images and preimages, ordered coordinate indices for projections, and the relevant set operands for each other operation. Representation/coordinate contracts are derived from those operands. Each registered operation declares a typed guarantee-transfer rule for its ordered input claims and emits a scoped output claim. Conversion, intersection, projection, image/preimage, and optimization do not share a generic guarantee ordering: a missing transfer rule, incompatible representation, or insufficient composed guarantee rejects the plan before any workspace or materialization begins. The rule is part of the selected adapter contract and provenance, so the verifier can audit the complete plan. Prepared execution runs the exact admitted operand payload; it cannot substitute another map or projection after admission. Stopped or rejected plans retain request identity, diagnostics, completed lineage, and any result evidence already produced.

For a complete-family request, every transformation must be exact/equivalent under its declared mathematical semantics unless a separately reviewed theorem establishes that the composed weaker operations still prove the requested coverage. Floating-point evaluation of an exact mathematical operation carries numerical support, not exact or validated evidence. Inner, outer, and heuristic approximations may run only when explicitly requested and must produce the matching partial/candidate relation; they are never a silent fallback for a complete-family plan. Keep expressions/lazy results where the selected adapter supports the required queries. Full representation conversion is an explicit materialization step, subject to the caller's size/resource budget and cancellation, with representation growth and evidence reported. Sampled support directions remain samples or declared enclosures, never an exact-set claim. Do not create a second operation registry unless concrete composition requirements cannot be expressed by the typed registrations.

For a complete-optimal-family request, the planner must reject any operation plan whose composed geometry guarantee cannot support the requested coverage claim; an inner/outer/heuristic relation may produce a candidate or partial outcome, never be relabelled complete. Each composed step carries input evidence identities and emits scoped output evidence, so a later verifier can audit the chain. The planner describes what registered operations promise; it does not prove the operation implementation correct or validate floating-point arithmetic.

**Class-map seam:** `GeometryPort`, `ConversionPort`, `ApproximationPort`, their request/outcome types, `GeometryOperationPlanner`, and `PreparedGeometryPlan`. **Tickets:** [GEO-02 #40](https://github.com/butahlecoq/controlled-systems-lab/issues/40), [GEO-04 #41](https://github.com/butahlecoq/controlled-systems-lab/issues/41), [GEO-08 #52](https://github.com/butahlecoq/controlled-systems-lab/issues/52), [GEO-03 #31](https://github.com/butahlecoq/controlled-systems-lab/issues/31).

The class map's candidate fixture proposal uses the established T-S01 `u ∈ [0,1]` full-family oracle and separate low-dimensional intersection, projection, and singular-image operator oracles. It keeps the `X1=[0,1/2]` intersection case separate from the first T-X01 baseline. These fixtures do not replace the owner-approved `u ∈ [-1,1]` assumption for newly authored baseline scenarios. Treat their dimensions and source-row counts as regression envelopes for those fixtures only; the operation profile, output limits, and global resource/capacity policy remain unresolved.

## 4. Immutable comparison definition and run identity

**Proposed default:** separate a caller-authored `ComparisonSpec` from the executed `ComparisonRun`. The spec identifies the resolved problem by content digest; effective strategy/profile and objective request; requested assurance and tolerances; requested outputs/projections and family target; selected strategy/algorithm/backend identities and versions; requested thread/memory policy; and repetition protocol. Its versioned canonical serialization produces a stable `ComparisonSpecId`; edits to any of these values create a new identity. The spec is immutable once execution begins. Requested settings live in the spec; effective settings and observed outcomes live in the corresponding run records.

Each individual strategy execution/repetition produces an immutable, content-addressed `RunRecordRef` that binds the same resolved-problem digest and effective request/profile identity to strategy/algorithm and backend identities/versions, build/configuration identities, effective numerical and resource settings, terminal outcome, assurance evidence, timings, resource observations, and raw measurement payload. The executed `ComparisonRunId` is derived from the `ComparisonSpecId`, the ordered complete set of individual `RunRecordRef` identities (including repetition indices and every terminal outcome), and the comparison schema version. Reruns append new records; they never overwrite a record or reassign an old identity. Thus equal source commits with different measured payloads cannot reuse a report/comparison identity.

Validate before pairing that both runs share the same problem, objective, profile/request, requested assurance, tolerances, output target, and repetition protocol. Record effective backend/config/resource differences explicitly; a required matched-backend comparison rejects mismatches, while an owner-permitted exception becomes a separately labelled comparison and cannot be pooled with matched runs. Preserve failed, unsupported, cancelled, resource-limited, and incomplete attempts alongside successes. Content addressing is over a versioned canonical encoding. V1 publication should put canonical immutable run records and their manifest in a self-contained comparison bundle, while all APIs and rendered links use `RunRecordRef`; a future store adapter may resolve those references externally only if digest verification and portability are preserved.

The execution/observation boundary records module timings and resource observations; the comparison layer aggregates stored records, not live workspaces. Timing records identify the measured phase and whether a span is inclusive of nested spans. Never add inclusive parent and child durations as if they were independent work; report wall time and additive module totals separately, with missing measurements marked unavailable. Correctness/trajectory HTML can be generated from an available run, but a comparative performance summary requires at least five tuned Release repetitions per strategy, alternating strategy order, and a separate limiter profile. The renderer validates identities/schema and renders the persisted family/trajectory data, raw measurements, tables, and explicitly labelled plots; it never calls a solver or recomputes a result. A sample cloud or selected witness plot is not a mathematical projection of the full family.

**Class-map seam:** `ComparisonSpec`, `ComparisonSpecId`, `RunRecordRef`, `ComparisonRun`, and `ComparisonRunId`, plus the saved-record renderer. This API shape refines the class-map comparison artifact decision; it does not decide storage location or publication host. **Tickets:** [OBS-04 #83](https://github.com/butahlecoq/controlled-systems-lab/issues/83), [EXP-02 #94](https://github.com/butahlecoq/controlled-systems-lab/issues/94), and the end-to-end comparison in [SYN-05 #71](https://github.com/butahlecoq/controlled-systems-lab/issues/71).

## Decisions that remain open for the owner

- **First scientific profile:** `nominal_open_loop` and the newly authored baseline bound `u ∈ [-1, 1]` are confirmed and are the proposed v1 experiment scope in the class map. Numerical coverage policy and the exact operation/capacity fixture remain open gates before a complete-family result is accepted. Feedback, uncertain-initial-state quantifiers, hybrid modes, process disturbance, and nonempty temporal coupling remain separate future profiles. Hybrid modes, guards, resets, and transitions are tracked in [EXT-07 #156](https://github.com/butahlecoq/controlled-systems-lab/issues/156). Restoring historical B04 inputs is a separate archival task, not a blocker for the new baseline.
- **Numerical acceptance contract (needed before a numerical result can be called a complete-family result):** review the evidence-guard migration, then choose/check tolerance fields, arithmetic profile, coverage procedure, acceptance thresholds, and independent checks for `NumericallySupportedCompleteness`. Recommendation: publish the method and diagnostics and use analytic fixtures; never imply validated or exact completeness. A request requiring `ValidatedCompleteness` must reject until a validated backend/verifier is available. This proposal does not set any coverage procedure or numerical threshold.
- **Geometry fixture profile (needed before geometry ticket acceptance):** review the candidate fixtures in the [class-level architecture](2026-10-12-class-level-system-architecture.md), then select the first exact/equivalent operation set, supported capacity policy, and any approved approximation relation. The proposed fixture dimensions and row counts are regression envelopes, not global caps or a claim that the current adapters support those operations. Recommendation: make the first complete-family path use only operation chains with reviewed transfer rules; test inner/outer approximation separately as candidate/partial output.
- **Runtime values and enforcement (needed before promising hard limits):** set worker/deadline/memory values and decide what limits each selected backend/platform can enforce. Recommendation: keep per-task algorithm serial in v1, schedule independent tasks in the outer executor, and record unknown/unavailable honestly; add permits only if a measured internal parallel workload justifies them.
- **Evidence validation method:** review the exact typed binding, coverage procedure, tolerance profile, and independent verifier checks before numerical completeness is accepted. The callable type shape is specified in the class map; it does not prove evidence correct by construction.
- **Comparison encoding/storage (needed before implementing persistence):** choose the canonical serialization/version and publication integration. Recommendation: ship a self-contained v1 comparison bundle with digest-verified immutable run records; keep `RunRecordRef` storage-agnostic so a later immutable external store can resolve the same identities. Embedding does not mean mutable or source-commit-only identity.
- **Publication details (needed before deploying a public report site):** choose hosting location, plot/export size limits, and any audience/access policy. The report contract already requires saved-data-only rendering, raw run evidence, timing semantics, and explicit plot scope.

These choices do not block revising or reviewing this proposal. The nominal scientific profile and new-baseline control bound are settled. Numerical coverage policy and the exact geometry operation/capacity fixture determine when the first implementation may claim a complete optimal family; storage/hosting and concrete resource values can be selected later against the proposed stable contracts. Historical B04 restoration remains separate archival work.
